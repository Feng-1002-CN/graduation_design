# 阶段 10：申报材料检查

> 依据竞赛规则对照校验报名表/附件完整性，给出缺漏清单与修正建议，降低申报返工。

## 1. 目标
用户选择目标竞赛 + 上传申报材料（报名表、作品说明、附件），系统依据该竞赛规则做完整性/格式校验，输出缺漏项与建议。

## 2. 前置依赖
阶段 00、01（规则来自竞赛信息管理）。

## 3. 验收标准
- [ ] 能列出某竞赛要求的材料清单（规则/报名说明驱动）。
- [ ] 对上传材料做完整性检查，标记缺失/不匹配项。
- [ ] 输出检查报告（缺漏项 + 建议）。

## 4. 范围

### In Scope
- 规则提取材料要求（LLM 结构化：必需材料列表）。
- 上传材料与要求对照检查。
- 检查报告生成。

### Out of Scope
- 不自动生成/填写报名表。
- 不做复杂表格字段级 OCR 校验。

## 5. 数据模型
```sql
CREATE TABLE application_check (
    id              BIGSERIAL PRIMARY KEY,
    competition_id  BIGINT NOT NULL REFERENCES competition(id),
    files           JSONB,                          -- [{name,type,url}]
    required_list   JSONB,                          -- 必需材料清单（规则提取）
    result          JSONB,                          -- [{item,status,advice}]
    created_at      TIMESTAMPTZ DEFAULT now()
);
```

## 6. API 契约

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/apply/check` | 提交材料检查 |
| GET | `/api/v1/apply/check/{id}` | 获取检查报告 |

请求/响应：
```json
// 请求
{ "competitionId": 1, "files": [ {"name":"报名表.pdf","url":"minio://apply/1.pdf"} ] }
// 响应 data
{
  "required": [ {"item": "报名表", "required": true} ],
  "result": [
    { "item": "报名表", "status": "OK", "advice": "" },
    { "item": "作品说明", "status": "MISSING", "advice": "缺少作品说明，请补充" }
  ]
}
```

## 7. 核心流程
1. 读取竞赛规则（active 规则）。
2. LLM 从规则中提取「必需材料清单」（结构化）。
3. 将上传文件与清单对照，标记 OK / MISSING / MISMATCH。
4. 生成建议并保存检查报告。

## 9. 关键实现要点与约束
- 材料要求提取必须基于规则原文（可溯源）。
- 检查结果给出明确 status（OK/MISSING/MISMATCH）+ 建议。
- 禁止编造要求（无规则依据时不臆造必需材料）。
